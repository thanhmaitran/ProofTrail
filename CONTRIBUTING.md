# Contributing

Thanks for your interest in ProofTrail. The project values small, well-tested
changes and honest documentation.

## Setup

```
python -m venv .venv
source .venv/bin/activate          # Windows: .\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev,visualization]"
```

## Before you open a pull request

```
ruff check .
ruff format --check .
python -m pytest
prooftrail corpus examples/manifest.json
```

All four must pass. CI runs the same checks on Python 3.12 and 3.13.

## Guidelines

- **Semantics first.** A change that affects what a verdict means must update
  `docs/formal-semantics.md` in the same pull request.
- **Never weaken a verdict rule.** `UNKNOWN` must not become `HOLDS`, and an
  error must not become `VIOLATED`.
- **Every bug gets a regression test** in `tests/regression/` that fails
  without the fix.
- **Independent expectations.** New corpus cases need a written `derivation`
  of the expected answer that does not rely on running ProofTrail.
- **Layering.** `model`, `exploration`, `properties` and `verification` must not
  import from `cli`, `reporting` or `visualization`.
- **No `eval`/`exec`** on anything that comes from a specification.
- **Claims need evidence.** Do not add performance or capability claims to the
  README without a test, a corpus case or a reproducible benchmark.
- Benchmark results are generated by `benchmarks/run_benchmarks.py`; never edit
  them by hand.

## Commit messages

Use a short imperative summary line (for example `Add AU counterexample
extraction`) and explain the reason for the change in the body when it is not
obvious.

## Reporting bugs

Include the specification (or a minimal version of it), the command line, the
output and the ProofTrail and Python versions. For security issues, follow
`SECURITY.md` instead of opening a public issue.
