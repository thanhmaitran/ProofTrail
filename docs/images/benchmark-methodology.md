# Benchmark methodology

The benchmarks answer concrete questions about ProofTrail itself. They are not
a comparison with other model checkers.

## Questions and experiments

| ID | Question | Experiment |
|---|---|---|
| E1 | How do time and memory grow with the number of reachable states? | `grid(n, 4)` for `n = 2..8` (16 to 65 536 states). |
| E2 | What does `packed` indexing change compared with `object`? | Same grid models, both indexings. |
| E3 | What does keeping predecessor links cost? | `explore(track_parents=False/True)`. |
| E4 | When does sharing one exploration or caching successors help? | 4 properties on `grid(6, 4)`, `shared`/`per-property` × cache on/off. |
| E5 | How does cost grow with the number of properties? | 1 to 64 invariants on `grid(6, 4)`. |
| E6 | How does counterexample length affect cost? | Chains with 100 to 30 000 step counterexamples. |

## Data

All models are generated by `benchmarks/generators.py`. Each generator has a
closed-form description of its state space (states, transitions, BFS depth), and
the runner **fails** if the engine disagrees. This protects against timing an
exploration that silently went wrong. No external data is used.

## Procedure

1. Parse the specification once; parsing is not timed.
2. One untimed warm-up run, then `repeats` timed runs (7 by default).
3. Garbage collection is run before and disabled during each timed region.
4. Time uses `time.perf_counter`; report median, min, max and standard
   deviation.
5. Peak memory comes from a **separate** run under `tracemalloc`, never from a
   timed run. `tracemalloc` measures Python allocations only; it is not process
   RSS.
6. Environment (Python, OS, CPU, ProofTrail version) and the exact
   configuration are written next to the results.

## Reproducing

```
python benchmarks/run_benchmarks.py            # full run, writes benchmarks/results/
python benchmarks/run_benchmarks.py --quick    # seconds, for a smoke test
```

Outputs: `results.json`, `results.csv`, `RESULTS.md` and the PNG charts, all
generated by the script.

## Interpreting results

* Absolute numbers depend on the machine. Compare ratios and growth, not
  milliseconds.
* The log-log slope of runtime against states is an *empirical exponent*. In
  the grid family the number of transitions per state grows with `n`
  (`2n(k-1)/k`), so a slope slightly above 1 is expected from `O(V + E)`.
* Differences smaller than about two standard deviations should not be read as
  real.
* The committed results come from one machine and one run; they are an example,
  not a guarantee. Re-run on your hardware before quoting numbers.

## Threats to validity

* The synthetic grid family has uniform structure; real models may behave
  differently (more skewed branching, longer guards).
* Only CPython on one machine was measured.
* Python-level `tracemalloc` overhead differs between variants, which can
  distort small memory differences.
* A successor cache pays off only when the same state is expanded several times
  (here: across several explorations). A single BFS expands each state once.
